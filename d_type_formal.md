# Региональная применимость D1 и D3: сильное обоснование и условия допуска

**Предлагаю ограничивать D через проверяемый механизм, а не через штраф за его высокие показатели.** Для D1 нужно обосновать региональный спрос на отдельную платную услугу и её дополнительную окупаемость. Для D3 — показать конкретные общие работы, совместимых участников и устранимые расходы. После этого строится фронт Парето.

Документ учитывает [d_type.md](d_type.md), актуальный `main` репозитория и присланный пользователем текст отчёта Claude «Фронт Парето: 60 портфелей» от 12.09.2026. В этом отчёте активны **D1 и D3**. D2, D4–D7 остаются резервными идеями, а не режимами текущего прогона.

Все ограничения ниже, кроме отдельно названных канонических, — **предлагаемая политика команды**. Это формализация для записки и следующего изменения инструмента; код и входные данные этим файлом не изменены. Числа лотов учебные: они не доказывают наличие реального рынка в соответствующих регионах.

## 1. Что означает результат уже выполненного перебора

Отчёт рассматривает D1 и D3 в отдельных прогонах с одной активной строкой D. После объединения вариантов без повторного учёта A/B/C получается:

```text
2 × C(8,4) × 4⁴ − C(8,4) × 3⁴ = 30 170 назначений.
```

Это не перебор пяти одновременно доступных режимов: он дал бы `70 × 5⁴ = 43 750` и разрешил бы смесь D1/D3 в одном портфеле. В текущем формате такую смесь не используем.

В присланном отчёте после проверки D3 остаётся 20 161 назначение, после канонических ограничений BASE/STRESS — 1056, на фронте — 60. Среди этих 60 нет чистых A/B/C; 18 не выдерживают замену D на A при прежнем составе лотов. Независимая реконструкция по описанию и доступному коду подтвердила эти числа и все приведённые min/max нормировки. **Это выводы конкретного прогона с принятыми коэффициентами и нормировкой, а не доказательство универсального превосходства D.** После новых ограничений числа и фронт нужно пересчитать.

Почему D3 настолько силён: при прежней пятёрке он сохраняет результат и поступления A, снижая расходы. Это улучшает сразу несколько связанных показателей — NPV, PI, kcash и SROI. Если экономия реальна, преимущество законно. Если она только предположена, несколько хороших метрик повторно отражают одну и ту же неподтверждённую гипотезу.

На момент написания этого файла в `main` был только `team_model.py` со `score_robust`, а `user_modes.py`, `pareto_search.py`, `pareto_report.py`, `pareto_html.py` и `PARETO_FRONT.md` находились в ветке `pareto_merge`. После слияния ветки все они доступны в `main`, и приведённые выше числа 1056 / 60 / 18 подтверждены прямым прогоном по этим исходникам.

## 2. Главный формальный фильтр: сначала допустимость D, потом Парето

Пусть `i` — лот, `d` — конструкция D1 или D3, `x(i,m)` — выбор режима, `P` — состав портфеля.

```text
x(i,m) ∈ {0,1};  Σ_m x(i,m) ≤ 1;  Σ_i,m x(i,m) = 4.
x(i,Dd) ≤ E(i,d; P).
E = NEED ∧ MECHANISM ∧ RESOURCES ∧ EVIDENCE.
```

| Условие | Что предъявить для допуска |
|---|---|
| NEED — местная задача | Получатель → доступный результат → действие; какой барьер или расход устраняем |
| MECHANISM — работающий способ | Для D1 — отделимая платная надстройка; для D3 — конкретный повторяющийся компонент |
| RESOURCES — возможность исполнить | Исполнители, смета, канал доставки, мощность, права на данные, финансирование обязательств |
| EVIDENCE — происхождение чисел | Источник или обозначенное проектное допущение каждого параметра; диапазон и сценарий отказа гипотезы |

Для хакатона не требуем уже подписанных договоров. Допустим **проектный паспорт** с модельным заказчиком, объёмом, тарифом и сметой. Но «сценарное допущение» нельзя называть «подтверждённым спросом». Пустое поле не означает допуск. Для реального внедрения проектные оценки нужно подтвердить.

Паспорта и правила фиксируются до ранжирования. Нельзя придумывать исключение для региона после того, как его портфель понравился по score. Обоснованное изменение гипотезы разрешено, но после него пересчитывается весь сравниваемый набор.

**Единая строка D:** одна выбранная конструкция и одна пятёрка для всех использующих её лотов. Обозначим через `K(i,d; P)` множество пятёрок, совместно обоснованных для лота и состава участников. Тогда:

```text
k_D ∈ пересечение K(i,d; P) по всем лотам портфеля с D.
```

Нельзя взять минимальные расходы от одной схемы и максимальные поступления от другой. Для D3 при изменении участников заново проверяются общая смета, распределение расходов и достижимость пятёрки. Если общей пятёрки нет, D остаётся у подходящего поднабора лотов либо команда явно расширяет формат модели.

**Отдельно фиксируем прогноз и проверку риска.** Основной фронт строится по одной общей номинальной пятёрке выбранного D; региональные нижние оценки служат тестом допуска и параметрами отдельных неблагоприятных сценариев. Например, проверка D1 при `θ_lower = 0.10` не меняет автоматически номинальное `θ = 0.20` и `k_commercial = 0.34`: такой фронт остаётся номинальным, его нельзя называть консервативным. Для D3 так же разделяются номинальные `s/e/h` и их согласованные неблагоприятные значения. Если выбираем консервативный фронт, сначала явно задаём общую поддержанную всеми выбранными лотами пятёрку и пересчитываем **все** метрики и кандидатов; одной проверки порога недостаточно.

**Общественное ядро — отдельное обязательство.** `public_core = true` требует бесплатного, недискриминационного и своевременного базового общественно значимого результата для всех заявленных получателей, с ресурсами на исполнение. Нельзя сузить круг получателей ради галочки или задерживать критическое предупреждение ради премиума. Государственный плательщик и высокий VPUB сами по себе флаг не доказывают.

Флаг в исходной таблице принадлежит режиму, поэтому каждый выбранный лот с D должен исполнять эти условия. Иначе общая строка D не получает `true`. Для D1 и D3 сохраняем результат A; новую общественную пользу заранее не добавляем.

## 3. Где D1 имеет экономическое основание

D1 — это A плюс отдельная платная надстройка. Региональный смысл — найти покупателя **дополнительной** услуги, сохранив бесплатный общественный результат. Ни название региона, ни высокая коммерческая база сами по себе продажу не доказывают.

Обозначения: `C0, O, V, A0, C` — исходные разовые затраты, годовые расходы, общественная ценность, якорные и коммерческие поступления лота. `A0` — сумма поступлений, не режим A. `I, L` — дополнительные разовые и годовые расходы; `R` — дополнительная годовая коммерческая выручка после замещения старых продаж, без повторного учёта якорного заказа.

```text
k_D1 = (1.05 + I/C0, 1.05 + L/O, 1, 1, 0.25 + R/C).
ΔNPV = −I + Σ_t (R_t − L_t)/(1+r)^t.
```

В прежнем примере `I = 0.02C0`, `L = 0.03O`, `R = θ(0.70−0.25)C`; принято `θ = 0.20`. Параметр θ — доля освоенного разрыва поступлений B–A, **не доля доказанно существующих покупателей**. При постоянных годовых потоках:

```text
AF(r,T) = Σ_t=1..T (1+r)^(-t).
θ* = [I/AF(r,T) + L] / [(0.70−0.25)C].
ΔNPV ≥ 0 тогда и только тогда, когда θ ≥ θ*.
```

Для таблицы используются 10 лет и 10% — допущения команды из `team_model.py`, не требования организаторов. `AF ≈ 6.14457`.

| Лот / регион | θ* | ΔNPV D1 против A при θ=0.20, млн руб. | Вывод для допуска D1 |
|---|---:|---:|---|
| FIRE / Сибирь | 0.228 | −2.71 | При прежних допущениях финансовая надстройка не окупается; оставляем A либо обосновываем другой спрос/смету |
| FLOOD / Дальний Восток | 0.188 | +1.50 | Малый запас: нужна особенно убедительная нижняя оценка продаж |
| AGRI / Юг | 0.057 | +47.34 | Арифметически хороший кандидат; проверить покупателей и разделение платных/базовых функций |
| INFRA / Урал–Поволжье | 0.072 | +37.12 | Кандидат при оплачиваемой аналитике объектов и сохранении критических предупреждений |
| ARCTIC / Арктика | 0.094 | +39.65 | Арифметика положительная, но услугу и мощность нужно обосновать отдельно; EO-механику сюда не переносим |
| TRANS / Центр | 0.068 | +34.63 | Кандидат при отдельном платном результате для перевозчика или владельца инфраструктуры |
| ENV / Волга–Каспий | 0.083 | +27.58 | Кандидат при отделимой аналитике конкретных объектов |
| SSA / федеральный | 0.087 | +31.19 | Нужны конкретный платный результат и права доступа; это не территориальный архетип |

### Предлагаемое самоограничение D1

**Для текущей конструкции, не добавляющей VPUB сверх A, допускаем надстройку по финансовому основанию только при `θ_lower ≥ θ*`.** `θ_lower` — заранее обоснованная консервативная оценка по тарифам, объёмам, мощности и замещению продаж. Если расходы неопределённы, порог считаем по соответствующей согласованной неблагоприятной смете, а не по самым дешёвым затратам из другого сценария.

Это дополнительное правило команды для **приращения D1**, а не требование положительного NPV всего общественного проекта. Долгосрочная субсидия допустима; её нельзя выдавать за коммерческую окупаемость надстройки. Если новый эффект D1 принципиально нефинансовый, его нужно отдельно описать и оценить: в прежней пятёрке такого эффекта нет.

Для сравнения: значение `θ_lower = 0.10`, если бы оно было обосновано, исключило бы FIRE и FLOOD по окупаемости, но сохранило бы остальные лоты по этому тесту. **0.10 не предлагается как универсальный норматив**: это иллюстрация того, как работают разные региональные пороги.

Паспорт продаж включает получателя, функцию, цену, годовой объём, источник оценки спроса и стоимость исполнения. Объём не превышает ни обоснованный спрос, ни мощность после бесплатного и якорного обслуживания. Одни поступления нельзя одновременно учитывать как якорные и коммерческие.

**Поправка к объяснению отчёта:** FIRE:D1 не может держаться на фронте «за счёт ядра» относительно FIRE:A: у них одинаковые ядро и VPUB. Отрицательный дополнительный NPV может сочетаться с улучшением kcash или PI всего портфеля; блочная сумма способна сохранить такой компромисс. Именно поэтому присутствие на фронте не заменяет отдельную проверку инвестиции D1.

## 4. Где D3 имеет технологическое и экономическое основание

D3 — это A с совместной закупкой или повторным использованием конкретной части работ. Сильная защита звучит так: **«мы устранили повторную оплату перечисленных работ, оставив региональную адаптацию и добавив стоимость координации»**.

Прежняя формула:

```text
k_c0   = 1.05(1 − s0·e0) + h0;
k_opex = 1.05(1 − sO·eO) + hO;
(k_vpub, k_anchor, k_commercial) = (1, 1, 0.25).
```

`s0,sO ∈ [0,1]` — доли общих работ в расходах A; `e0,eO ∈ [0,1]` — устранимая доля расходов этих работ; `h0,hO ≥ 0` — расходы координации в долях исходных C0 и O. Прежний пример: `(s0,e0,h0)=(0.20,0.30,0.02)`, `(sO,eO,hO)=(0.25,0.20,0.02)`. Отсюда `(1.007,1.0175,1,1,0.25)`. Эти доли — гипотезы, не нормативы для всех регионов.

Условия экономии: `1.05·s0·e0 > h0` и `1.05·sO·eO > hO`. При прежних долях пороги `e0 > 9.52%`, `eO > 7.62%` относятся к **общей части** затрат. Порог безубыточности не доказывает достижимость значения выше него.

### Усиливаем существующее условие общей группы

Реконструкция чисел прогона соответствует следующему правилу: как минимум два лота **именно в D3**, и пересечение групп **всех** D3-лотов непусто. Подходящий партнёр только в A/B/C этого условия не исполняет. Это полезный предварительный фильтр, но широкий класс EO или PNT/InSAR не определяет одинаковые данные, покрытие, сроки, разрешение, алгоритмы или права использования.

Для предлагаемой единой совместной схемы нужны:

1. Не менее двух выбранных участников D3 и общий для них идентифицированный компонент. Проверка одной подходящей пары не даёт скидку третьему несовместимому лоту. Внешнее уже оплаченное ядро допустимо обсуждать только как отдельное расширение текущего правила, с указанием владельца и затрат.
2. Совместимые требования каждого участника к этому компоненту: данные, территория, периодичность, сроки, качество, права и способы использования.
3. Общая смета с перечнем исходных дублирующихся работ, устранимых расходов, местной адаптации и координации. Нельзя списать всю стоимость лота в «общее ядро».
4. Распределение общей стоимости между участниками: сумма долей равна общей стоимости. Нельзя несколько раз вычесть одну экономию или оставить расходы общего оператора за пределами проекта.
5. Сохранение базового доступа, качества и сроков. При оплате по затратам экономия может уменьшить якорный заказ — неизменное `k_anchor = 1` тогда требует отдельного основания.
6. Повторная проверка сметы и пятёрки при изменении состава участников. Наличие второго участника само по себе не подтверждает прежний процент экономии.

**Конкретный тест:** FIRE:D3 + ENV:D3 приписывает общей схеме экономию 25.8 млн руб. C0 и 5.2 млн руб./год OPEX относительно A. Паспорт должен объяснить именно эти суммы. Запись «оба EO» не подтверждает ни одного рубля из них.

### Региональная карта: что действительно можно пытаться объединить

В таблице указаны **направления проверки**, а не утверждение о существующей совместимости. География объясняет задачу и местную адаптацию; технический компонент и смета определяют допуск.

| Лот / регион | Обоснование D1: кому и за что платить | Обоснование D3: потенциальная общая часть | Что удерживает от автоматического допуска |
|---|---|---|---|
| FIRE / Сибирь | Индивидуальная аналитика активов, интеграция, отчётность; критические предупреждения остаются бесплатными | С FLOOD/ENV: каталог, лицензия на подходящие данные или часть обработки | Местные карты, пороги и реагирование не исчезают; D1 при θ=0.20 не окупается |
| FLOOD / Дальний Восток | Аналитика объектов и интеграция сверх своевременного базового предупреждения | С FIRE/ENV: только действительно одинаковые входы и операции | Гидрологические настройки и доставка предупреждений остаются; D1 почти на границе окупаемости |
| AGRI / Юг | Услуга для хозяйства: индивидуальная аналитика и интеграция при ясно описанном общественном слое | EO с FIRE/FLOOD/TRANS/ENV; PNT/InSAR с INFRA/TRANS — только по конкретному компоненту | Гектары не заменяют смету и подтверждённый спрос; сезонность и точность могут требовать иных данных |
| INFRA / Урал–Поволжье | Дополнительные отчёты и интеграция по объектам с сохранением критического результата | С AGRI/TRANS: совместимые исходные данные, опорные элементы или обработка PNT/InSAR | Мониторинг деформаций и навигационные задачи не становятся одинаковыми из-за общей метки группы |
| TRANS / Центр | Отдельный платный пакет для перевозчика/владельца объекта, с обоснованным базовым общественным результатом | EO с соответствующими лотами; PNT/InSAR с AGRI/INFRA | Проверяются точность, задержка, частота обновления и права; число перевозчиков не доказывает продажи |
| ENV / Волга–Каспий | Аналитика конкретных объектов сверх общего экологического результата | С FIRE/FLOOD: подходящая закупка данных, каталог или общие операции обработки | Местные карты и интерпретация остаются; само открытие данных не доказывает весь общественный эффект |
| ARCTIC / Арктика | Только отдельно описанная надстройка для логистики/связи с покупателем и свободной мощностью | Вне основной области D3 до отдельного разбора: потенциальное пересечение PNT/InSAR, но не общая SATCOM-экономия | Высокие C0/OPEX и иной состав услуги; EO-проценты не переносим; общая метка PNT/InSAR не создаёт общий канал связи |
| SSA / федеральный | Отдельный результат для названного заказчика, с правами доступа и сохранённым общественным пакетом | Нет второго SSA-лота в текущем наборе; внутреннюю совместную схему D3 не обосновать одной меткой SSA | Положительный расчётный ΔNPV не доказывает продажи; внешнее ядро потребует нового паспорта и явного расширения |

Практический приоритет: для **D1 сначала исследовать AGRI, INFRA, TRANS, ENV**, затем пограничный FLOOD; FIRE при прежних числах оставить A. ARCTIC/SSA требуют отдельного описания самой надстройки. Для **D3 сначала разбирать конкретные пары FIRE–ENV, FLOOD–ENV, FIRE–FLOOD**, затем EO-компоненты AGRI/TRANS и компоненты PNT/InSAR AGRI/INFRA/TRANS. Это порядок подготовки доказательств, а не заранее назначенные победители.

## 5. Главная защита от «имбы»: провал гипотезы дороже простой замены D на A

В отчёте полезно проверяется замена D → A. Она отвечает на вопрос: **можно ли до запуска отказаться от конструкции D и выбрать обычный A?** Но после начала реализации уже понесённые расходы не исчезают.

| Проверка | D1 | D3 |
|---|---|---|
| Отказ до запуска, когда расходы ещё не понесены | Можно сравнить с чистым A | Можно сравнить с раздельным A |
| Гипотеза провалилась после начала работ | При R=0 остаются I и обязательная поддержка L | При e0=eO=0 остаются координация h0,hO и местные работы |
| Дополнительный риск | Продажи ниже плана, замещение старых продаж, перегрузка базового сервиса | Меньше общей части, несовместимость, рост адаптации, концентрация у общего оператора |

**Следовательно, «безопасный откат в A» не означает устойчивость уже начатого D.** При полном провале экономии и сохранении прежних координационных расходов D3 имеет `(k_c0,k_opex)=(1.07,1.07)`, а не `(1.05,1.05)` режима A.

| Представитель из отчёта | C0 с прежним D3 | C0 при чистой замене D3 → A | C0 без экономии, с сохранением координации | Последствие при лимите 1180 |
|---|---:|---:|---:|---|
| №1: FLOOD:D3, AGRI:C, TRANS:C, ENV:D3 | 1124.14 | 1150.80 | 1163.20 | По C0 проходят все три; запас после провала меньше |
| №22: FIRE:D3, AGRI:D3, TRANS:D3, ENV:D3 | 1117.77 | 1165.50 | 1187.70 | «Безопасный откат» проходит, но провал после расходов превышает лимит на 7.70 |
| №30: FIRE:D3, FLOOD:D3, AGRI:D3, TRANS:D3 | 1178.19 | 1228.50 | 1251.90 | Даже чистая замена на A нарушает STRESS |

Все суммы — млн руб. Одного C0 недостаточно: остальные ограничения и финансирование также проверяются. **В дополнительном сценарии полного отказа гипотезы** (D3: нулевая экономия при сохранении координации; D1: нулевая дополнительная выручка при сохранении вложений и расходов) недопустимы **22 из прежних 60**. По сравнению с чистой заменой в A дополнительно отпадают №6, №7, №8 и №22. Это отдельная проверка команды, не результат исходного отчёта и не новый канонический STRESS.

Поэтому вариант №22 нельзя называть устойчивым к провалу D3 только на основании безопасной замены в A. Нужны обоснованная нижняя граница экономии, решение до расходования средств и план действий при неудаче, либо другой портфель.

### Предлагаемое правило финального допуска

- Для D1: обоснованная нижняя оценка спроса проходит тест дополнительной окупаемости; отдельно показан более тяжёлый сценарий без продаж и его финансирование.
- Для D3: нижняя обоснованная оценка общей части и экономии, вместе с согласованной верхней оценкой адаптации/координации, сохраняет заявленный результат и выполнимость портфеля. Проверяется и более тяжёлый сценарий провала.
- При непрохождении тяжёлого сценария не скрываем риск: указываем, можно ли остановить расходы до запуска, отложить надстройку, заменить режим или пересобрать портфель. После запуска нельзя объявлять уже потраченные деньги возвращёнными.
- Источник покрытия расходов и общественные обязательства должны быть согласованы. Долгосрочная субсидия допустима, но не отменяет лимиты C0/OPEX и остальные условия кейса.

Не требуем, чтобы при любом мыслимом событии сохранялись все преимущества. Требуем отличать **расчёт на обоснованном консервативном сценарии**, **крайний риск** и **реальный управленческий ответ**. Без источника нижней оценки нельзя обещать гарантированную выгоду.

## 6. Как выбирать после ограничений, не искажая Парето

В присланном отчёте три блока:

```text
F_fin     = z(NPV) + z(PI) + z(kcash);
F_public  = z(VPUB) + z(SROI) + z(public_core_lots/4);
F_quality = z(t_rep) + z(readiness) + z(resilience) + z(scale).
z(q) = (q − min(q)) / (max(q) − min(q)).
```

Портфель X доминирует Y, если не хуже по всем трём блокам и строго лучше хотя бы по одному. Деньги и общественная ценность не складываются в единый денежный поток. Но внутри блоков уже приняты предпочтения: компоненты имеют равный вес **после** нормировки.

**Три уточнения для защиты:**

1. Нормировку считаем на общем наборе допустимых кандидатов обоих отдельных прогонов D1/D3, а не отдельно для каждого. После изменения допуска фронт строим заново из всех оставшихся кандидатов, а не просто удаляем строки из прежних 60: ранее доминируемый вариант может стать недоминируемым. Для сравнения «до/после» дополнительно сохраняем прежний эталон min/max, чтобы не спутать изменение экономики с изменением масштаба. При `max=min` одинаковой компоненте назначаем общий нулевой вклад.
2. NPV, PI и kcash связаны между собой; SROI повторно использует VPUB и затраты. Это не двойной денежный счёт, но фактически усиление веса связанных свойств. Нужно объяснить такой выбор и проверить чувствительность, например к исключению PI или SROI. Фронт по трём суммам не равен фронту по десяти исходным показателям.
3. Окупаемость отдельного D1 не равна окупаемости всего портфеля. В доступной модели `PI = PV(CASH−OPEX)/C0 = 1 + NPV/C0`: граница окупаемости PI=1, а не 0. Отрицательный NPV при положительном операционном потоке допустим для субсидируемой инфраструктуры. Слова «убыточны по PI» лучше заменять точным «PI ниже 1 при принятом горизонте и ставке».

После построения нового фронта показываем представителя по деньгам, по общественной пользе и разумный компромисс, каждый — с региональным паспортом и неблагоприятными сценариями. «Минимальная сумма рангов» из отчёта — возможный способ выбрать компромисс, но не доказательство единственного объективно лучшего решения; равные ранги и чувствительность к составу кандидатов требуют прозрачного правила.

Условие отсутствия ARCTIC/SSA на прежнем фронте тоже не является региональным запретом. Оно описывает этот набор данных и эти предпочтения. Особая региональная задача может обосновать иной заранее объявленный критерий или ограничение, но не бесплатный бонус к коэффициентам D.

Отдельно: `score_robust = min(score_base, score_stress)` из доступного `team_model.py` — другой способ ранжирования. При фиксированном портфеле и неотрицательных весах `score_base − score_stress = w_capex·C0·(1/1180−1/1300) ≥ 0`, поэтому он равен `score_stress`. Эта метрика проверяет смену бюджетного лимита, а не неопределённость спроса/экономии D, и её нельзя подставлять вместо описанного фронта Парето без объявления смены метода.

## 7. Что нужно реализовать и предъявить

**Паспорт каждой допущенной схемы:** лоты и участники; получатель и результат; бесплатные и платные функции; заказчик; смета; ресурсные ограничения; происхождение параметров; консервативный сценарий; крайний риск; ответственный и критерий приёмки. Для D3 паспорт общий на схему с распределением затрат по лотам, а не независимые скидки для каждого.

**Порядок следующего изменения инструмента:**

1. Зафиксировать версию входов, конструкцию D, диапазоны и правила допуска. Проверить конечность коэффициентов, положительность затрат и неотрицательность якорных/коммерческих поступлений; чистый поток может быть отрицательным.
2. Фильтровать разрешённые пары «лот — режим» и затем совместимость/общие ресурсы целого портфеля. Ту же политику применять при ручной оценке, переборе и анализе чувствительности, чтобы ручной ввод не обходил ограничение.
3. Сохранить девять канонических проверок `case_core.check_constraints` в BASE и STRESS. Вывести отдельно командные проверки D с фактом, порогом, основанием и причиной отказа.
4. Пересчитать общий набор кандидатов, нормировку и фронт. В отчёте отделить чистую замену D → A до запуска от срыва гипотезы с сохранением понесённых расходов.
5. На приёмке проверить допустимую схему и отказ: D1 со спросом ниже порога; D3 без общего компонента, с несовместимым третьим участником или с нераспределённой общей стоимостью. Это проверки будущей реализации, а не уже выполненные функции.

Не вводим произвольный лимит «не более двух D». Если ограничивает команда внедрения, сравниваем требуемые часы с доступными; если бюджет общего заказчика — обязательства с бюджетом. Исходные индексы, география и группы возможностей автоматически от выбора D не меняются. Сохраняются ровно четыре лота, минимум три нефедеральных архетипа, две группы возможностей и два общественных ядра.

## 8. Сильная формулировка по критериям

«Мы используем D там, где региональная задача позволяет исполнить его механизм. У D1 дополнительная коммерческая услуга должна покрывать собственные вложения при обоснованной консервативной оценке спроса. У D3 каждый рубль экономии относится к указанной устранимой работе, а совместная смета включает региональную адаптацию и координацию. Бесплатный общественный результат сохраняется. Неподтверждённая гипотеза не получает автоматический допуск только потому, что улучшает несколько метрик. Итоговый портфель сравнивается с A/B/C и проверяется на последствия провала выбранного механизма».

| Критерий | Что именно доказываем |
|---|---|
| П1 | Для каждого региона: потребность → сервис → действие → общественный эффект; пользу не заменяем выручкой |
| П2, П4 | Происхождение пятёрки, область применимости, единое сравнение альтернатив, ограничения и чувствительность фронта |
| П3 | Плательщик, расходы новых обязательств, сроки оплаты, дополнительная окупаемость D1 и покрытие дефицита проекта |
| П5 | Кто закупает, исполняет, принимает результат и несёт риск; точная граница бесплатного доступа |
| П6 | Последствия уменьшения бюджета в официальном STRESS и обоснованное сохранение либо изменение портфеля |
| П7 | Риски спроса, несовместимости и общего оператора; последствия срыва D, меры и пределы их действия |
| П8 | Что используется повторно, что адаптируется в регионе, какие результаты пилота передаются следующему участнику |
| П9 | Этапы проверки до затрат, ответственные, ресурсы, критерии приёмки и источники измерения результата |

D2, D4, D5, D6 из [d_type.md](d_type.md) не объявляются плохими только потому, что исключены из текущего прогона. Это другой предмет следующей проработки: оплаченный базовый доступ, разделимые пакеты A/B, якорный резерв, переносимость. D6 при прежней пятёрке дороже C и требует отдельного основания по рискам; D7, среднее A/B/C, при неотрицательных предпочтениях доминируется B. В текущем документе они не используются для улучшения фронта задним числом.
